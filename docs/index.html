Pipeline / connected components

From photons to a fix.

Follow one position through the system. Each step names the component, the signal it receives, and the hand-off it creates for the next stage.

Step 01 / 07

The line is the data path. Scroll through it as a sequence: an image becomes a map, a map becomes observations, and observations become a position estimate that can be measured against truth.

  1. 01
    Input / captureimage + UTC

    Start with a time-stamped sky

    A RealSense frame enters the live pipeline with its capture time. During a simulated evaluation, a service supplies a known location and UTC time instead, so the same downstream path can be exercised without the camera.

    Receives
    camera image or GPS request
    Hands off
    image with a precise timestamp
  2. 02
    Sky map / normalise/sky_map

    Make one consistent view of the sky

    sky_mapper applies calibration and unwraps the camera image into an equirectangular panorama. The simulator can create an equivalent map from six Stellarium views, giving tests the same topic shape as live input.

    Receives
    calibrated image or rendered faces
    Hands off
    equirectangular sky map
  3. 03
    Celestial detectorcandidate points

    Find useful lights in the image

    celestial_detector looks for stars, the Sun, and the Moon. It records where each candidate appears in the panorama and attaches a confidence and object type to the observation.

    Receives
    /sky_map
    Hands off
    celestial observations
  4. 04
    Catalogue / identifyevidence

    Turn bright points into identities

    Star candidates can be projected through virtual perspective tiles and matched against the offline catalogue. Identified stars give the solver named celestial references instead of anonymous image points.

    Receives
    candidate positions and brightness
    Hands off
    identified objects and confidence
  5. 05
    Celestial localiserpose solve

    Compare what was seen with what should be seen

    celestial_localiser uses the observation timestamp and ephemeris predictions to solve for latitude, longitude, and heading. It rejects unusable evidence, then searches for the pose that best explains the remaining directions.

    Receives
    observations + ephemeris
    Hands off
    estimated pose and confidence
  6. 06
    ROS outputspose + fix + TF

    Publish a position other nodes can use

    The solved pose is published to the ROS graph as a pose, a geographic fix, and optional transforms. Debug files preserve the timestamped result so a run can be inspected after the live pipeline has moved on.

    Publishes
    /celestial_pose and /celestial_fix
    Preserves
    pose and observation debug files
  7. 07
    Evaluation / measureCSV metrics

    Measure the distance to truth

    The random evaluator samples surface positions, waits for the matching timestamped pose, and appends ground truth, estimate, object count, and haversine error to the metrics CSV. This dashboard turns those rows into the globe, summary, and run list.

    Compares
    ground truth against estimated fix
    Publishes
    random_localisation_metrics.csv
  8. 08
    Future / satellite layerWIP

    Add predictable moving references

    Satellite observations could add another sky layer with known orbital motion. The planned stage would detect and reject or identify satellites, then pass their time-dependent directions into the same observation interface.

    Would receive
    moving sky detections + time
    Would hand off
    satellite candidates and tracks
  9. 09
    Future / aircraft layerWIP

    Use aircraft as relative motion cues

    Aircraft detection and rejection are future work. When tracked over time, an aircraft could become a source of differential motion or be excluded when it conflicts with the stable celestial solution.

    Would receive
    frame-to-frame moving objects
    Would hand off
    tracks, confidence, and exclusions
  10. 10
    Future / cloud layersWIP

    Read the atmosphere as a layered map

    Cloud classification and tracking could provide local motion and atmospheric structure when stars are obscured. The roadmap separates high-, mid-, and low-altitude clouds because each layer carries a different reliability and motion model.

    Would receive
    cloud texture and temporal tracks
    Would hand off
    layer estimates and motion cues
  11. 11
    Future / horizon layerWIP

    Anchor the sky to local terrain

    Horizon shape and nearby terrain could constrain the camera pose when the sky is only partly visible. This stage would connect the spherical sky representation to a local geometric or visual map.

    Would receive
    horizon profile and terrain features
    Would hand off
    local scene constraints
  12. 12
    Future / adaptive fusionWIP

    Choose the reliable layers in context

    A future fusion stage could adapt to weather, time of day, motion, and visibility. It would weight stars, satellites, aircraft, clouds, terrain, and IMU data according to which observations are trustworthy at that moment.

    Would combine
    available sky and motion layers
    Would produce
    condition-aware pose confidence
